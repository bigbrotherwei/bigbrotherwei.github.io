FoundationDB（FDB）的 2021 年 SIGMOD 论文回答了一个很实用的问题：怎样让一个支持严格可串行化事务的有序 KV 存储，同时具备横向扩展、快速故障恢复和可验证的正确性？论文的答案不是给每个分片塞进一套完整事务协议，而是把**事务决策、持久日志、数据存储和集群协调**拆成不同角色。理解这些角色如何协作时，还需要把论文中的历史测量与今天的部署判断区分开来。

这张图把读路径、提交路径和控制平面分开画。客户端先从 Proxy 获取读取版本，随后可直接向 Storage Server 读取该版本的数据；写入暂存于客户端，提交时再交给 Proxy。Coordinators 与 Cluster Controller 主要处理选举、成员和角色招募，不位于每次读写的数据路径上（原论文 §2.3–§2.4）。

## 一笔事务怎样提交

1. 客户端取得 read version，在同一版本上读出快照；写操作先缓存在本地。
2. 提交时，Proxy 从 Sequencer 获得提交版本，把事务的读写冲突范围交给 Resolver 检查。
3. 没有冲突的变更被发送到 LogServer，达到配置要求的持久化确认后，Proxy 才向客户端报告提交成功。
4. Storage Server 稍后从日志拉取属于自己分片的变更，更新可供读取的多版本数据。

这套流程把“提交已经持久”与“存储节点已经应用”分开。MVCC 负责按版本读，乐观并发控制（OCC）负责冲突判定；只读事务通常不走完整写入提交路径。原论文还指出：某些跨 Resolver 的冲突检查会出现保守的误判，导致本可提交的事务被拒绝；因此不能把冲突检测描述成零误报（§2.4.2）。

FDB 的 Storage Server 管理的是 key range 分片，不是每片一个独立的 Raft 主节点。理解这一点后，再看全局版本、Resolver 和 LogServer 的职责就不容易混淆。进程角色、恢复自举和实验集群部署的细节可参见[FoundationDB 架构与事务机制](/posts/foundationdb-architecture/)。

## 恢复为何可以快

当事务系统中的关键角色故障时，Cluster Controller 可以重新招募 Sequencer、Proxy、Resolver 和日志角色。恢复阶段利用 Coordinators 保存的旧日志配置信息确定新的恢复边界；旧日志中的已提交变更仍可由 Storage Server 继续消费。它不要求先把整个数据集复制完，才重新开放新事务（§2.5）。日志副本通常同步参与提交，而 Storage Server 的副本异步追赶，两个层次的“复制”不能混成一回事。

论文对跨区域部署还给出更复杂的卫星站点和故障切换方案（§3）。关键取舍是：主区域内同步保留日志副本，可以避免正常提交每次都等待跨区域 WAN；但远端复制是异步的，极端的整区域同时故障仍涉及持久性与可恢复性的边界，不能简化成“任何故障都零丢失”。

## 论文里的另一个主角：确定性模拟

FDB 将生产数据库逻辑放入可复现的离散事件模拟环境，网络、磁盘、时间和随机源都由模拟器控制；再叠加故障注入、随机工作负载和断言检查。罕见故障一旦出现，可以用相同随机种子重放，而不必等待线上再次碰巧复现（§4）。这一方法对正确性和恢复路径尤其有价值，但论文也承认：模拟不能可靠地替代真实性能测试，也不能覆盖其控制之外的第三方库或操作系统契约。

## 怎样读性能数据

论文的生产测量来自 2020 年前后的特定跨区域集群，包含约 58 台机器和 292 TB 数据。文中给出的平均读延迟约 1 ms、平均提交延迟约 22 ms，是**那套部署、那段观察窗口**的结果，不是当前版本的普遍 SLA（§5.1）。另一组单数据中心合成负载显示，机器数从 4 台增至 24 台时，读写吞吐都有明显提升，但不同角色会在不同负载下先到达 CPU 或存储瓶颈（§5.2）。289 次生产重配置的样本里，中位恢复时间为 3.08 秒（§5.3）；该数字同样不能脱离配置和故障类型单独使用。

作者还强调短 MVCC 窗口的代价：论文描述的窗口为 5 秒，长事务需要拆分或重试（§6.4）。所以“严格事务 + 快速恢复”不等于“任意长、任意大的事务都适合直接运行”。

## 我的阅读结论

这篇论文最值得学习的是**明确的职责边界**：版本与冲突检查负责事务顺序，日志先兑现持久性，存储节点异步服务读和最终数据，控制平面负责招募与恢复。它把系统复杂度转移到了角色协作和测试基础设施上；确定性模拟正是让这种复杂架构可以持续演进的重要配套，而不是发布前补几轮故障演练就能替代的东西。
