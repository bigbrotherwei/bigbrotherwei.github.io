# 个人博客重构设计文档

日期：2026-09-16  
仓库：`bigbrotherwei/bigbrotherwei.github.io`  
当前线上分支：`master`  
目标站点标题：`bigbrotherwei`

## 1. 概述

本次重构目标是把当前博客从“已生成的 Hexo 静态产物仓库”升级为一个可长期维护、可持续扩展、可通过 PR 协作更新的现代静态博客工程。

新站点会参考 `hexo-theme-fluid` 的整体气质：沉浸式首屏、大图封面、透明导航、Material 风格卡片、清晰的文章阅读体验和暗色模式。但实现上不直接复制 Fluid 源码，不引入 Fluid 主题依赖，也不把项目继续限制在 Hexo 主题结构里。

第一批实现重点是博客基础能力：工程框架、视觉系统、首页首屏、文章系统、专题系统、实用工具入口、项目页、关于页和 GitHub Pages 自动发布。访问统计和当前在线人数会写入整体设计，但明确放到后续阶段，不进入第一批实现范围。

## 2. 当前状态

远端仓库目前主要是 2021 年生成后的 Hexo 静态文件，包括：

- `index.html`
- 哈希命名的 JavaScript 和 CSS 文件
- 文章归档目录
- 字体和图片资源

仓库中没有完整的 Hexo 源码工程，也没有可维护的文章内容结构、构建脚本、依赖清单或 GitHub Actions 发布流程。

本地工作区当前是一个新的 `main` 分支仓库。后续实现开始前，需要把它建设成源码仓库，并连接到 GitHub 远端。

## 3. 目标

- 用源码工程替代当前已生成的静态产物。
- 使用 `bigbrotherwei` 作为站点主标题和品牌标识。
- 独立实现一套 Fluid-inspired 视觉风格。
- 首页采用原创手绘农场暮景首屏。
- 首屏每日展示一条中文名人名言。
- 支持文章、专题、归档、标签、项目、关于页和实用工具。
- 后续维护采用 feature branch -> PR -> merge -> publish 流程。
- 合并后通过 GitHub Actions 自动发布到 GitHub Pages。
- 控制第一批范围，让站点可以稳定上线。

## 4. 第一批非目标

第一批不做以下内容：

- 不复制或修改 `hexo-theme-fluid` 源码。
- 不实现访问统计和在线人数。
- 不实现依赖后端的工具。
- 不增加登录、用户中心或私有后台。
- 不一次性迁移所有历史文件。
- 不引入 CMS，除非后续维护需求明确需要。
- 不实现评论系统。

## 5. 技术架构

推荐使用 Astro + Markdown/MDX + TypeScript 构建。

技术栈建议：

- Astro：页面路由、布局、静态生成。
- TypeScript：站点配置、数据结构和工具逻辑。
- Markdown/MDX：文章和长内容页面。
- CSS variables + 组件级 CSS：设计系统和主题变量。
- Shiki 或 Astro 集成代码高亮：代码块渲染。
- Pagefind：后续实现静态搜索。
- GitHub Actions：构建和发布。

选择 Astro 的原因：

- 静态站性能好。
- 写作体验适合 Markdown。
- 页面和组件结构清晰。
- 适合做文章、专题、工具页这种混合型站点。
- 比继续维护旧 Hexo 生成物更利于长期演进。

## 6. 分支与发布模型

目标分支模型：

- `main`：保存源码、文章、配置、文档。
- GitHub Actions：从 `main` 构建站点。
- GitHub Pages：发布构建产物。
- 后续需求通过功能分支开发，再创建 PR。

发布流程：

1. 从 `main` 创建功能分支。
2. 完成页面、文章或工具开发。
3. 本地构建验证。
4. 推送远端分支。
5. 创建 PR。
6. Review 后合并。
7. GitHub Actions 自动构建并发布。

项目 README 需要说明：

- 如何安装依赖。
- 如何本地运行。
- 如何新增文章。
- 如何新增工具。
- 如何发布。
- 后续如何通过 PR 维护。

## 7. 视觉方向

整体视觉参考 Fluid，但实现必须原创。

可参考的 Fluid 气质：

- 沉浸式首屏。
- 大图封面。
- 顶部透明导航。
- 滚动后的毛玻璃导航。
- Material 风格卡片。
- 舒适的文章排版。
- 文章页目录。
- 暗色模式。
- 本地搜索体验。

本站自己的视觉关键词：

- 手绘农场暮景。
- 安静。
- 温暖。
- 手账感。
- 技术感。
- 克制。
- 中文阅读友好。
- 蓝黑、草绿、泥土棕为主。
- 少量琥珀色或青色作为强调色。

避免：

- 过度赛博朋克。
- 过度饱和的霓虹色。
- 营销型首页。
- 大量无意义动效。
- 纯装饰性的渐变球、光斑、漂浮元素。
- 让人感觉像通用模板的素材图。
- 直接复制第三方游戏素材、贴图、角色或 UI。

## 8. 首页设计

首页首屏采用原创手绘农场暮景：树林、木屋、田地、道路、桥梁和水岸构成有纵深的背景层，保留 Fluid 式“大图封面 + 居中标题 + 每日名言”的结构，但视觉资产完全由本站独立生成和实现。

首页、文章列表、专题列表、实用工具、项目和关于页分别使用不同场景。每篇文章详情和每个专题详情也必须有独立背景，不与其他内容共用同一张图。所有背景保持统一的蓝调暮色、暖色灯光和细腻手绘质感，只在地点、建筑、道路、水岸和构图上变化。桌面和移动端使用同场景的独立裁切资源，避免仅依赖 `background-position` 导致移动端丢失视觉主体。

首屏内容：

- 主标题：`bigbrotherwei`
- 副内容：每日中文名言
- 名言出处：作者和作品名
- 底部：向下滚动提示

导航行为：

- 页面顶部时透明。
- 滚动后变成半透明毛玻璃背景。
- 桌面端显示完整导航。
- 移动端折叠菜单。

首屏下方内容区：

- 最新文章。
- 精选文章。
- 专题入口。
- 实用工具入口。
- 项目展示。
- 关于作者的简短入口。

首页不做纯营销页，也不做只有文章列表的传统博客首页。它应该先通过手绘农场暮景和每日名言建立氛围，再自然进入内容。

## 9. 每日名言模块

每日名言模块使用本地数据，不依赖外部 API。

要求：

- 中文为主。
- 第一版内置不少于 100 条。
- 后续可扩展到 365 条。
- 同一天所有访问者看到同一句。
- 第二天自动切换。
- 不提供手动切换按钮。
- 不请求第三方名言服务。
- 优先选择可核验出处的经典名言。

数据结构：

```ts
type Quote = {
  text: string;
  author: string;
  source?: string;
  tags: string[];
};
```

示例：

```ts
{
  text: "知者不惑，仁者不忧，勇者不惧。",
  author: "孔子",
  source: "论语",
  tags: ["修身", "勇气"]
}
```

展示效果：

```text
知者不惑，仁者不忧，勇者不惧。
-- 孔子《论语》
```

名言来源建议：

- 中国古典：论语、孟子、庄子、道德经、史记、诗词。
- 世界文学：莎士比亚、歌德、雨果、托尔斯泰等。
- 哲学思考：苏格拉底、尼采、罗素等。
- 科学与创造：爱因斯坦、居里夫人、费曼等。
- 行动与成长：适合每天打开博客时看到的句子。

需要避免：

- 来源不明的网络鸡汤。
- 常见但未经证实的伪名言。
- 可能涉及版权风险的现代长文本翻译。

## 10. 导航与信息架构

主导航：

- 首页：`/`
- 文章：`/posts`
- 专题：`/topics`
- 实用工具：`/tools`
- 项目：`/projects`
- 关于：`/about`

辅助页面：

- 归档：`/archive`
- 标签：`/tags`
- 分类：`/categories`
- 搜索：`/search`

文章、专题、分类、标签的区别：

- 文章：单篇内容，通常按时间发布。
- 专题：围绕一个主题组织的一组文章，有顺序、有导读、有持续更新。
- 分类：内容的大方向。
- 标签：细粒度关键词。

示例：

- 文章：《如何用 GitHub Actions 发布博客》
- 专题：《个人博客重构实录》
- 分类：技术笔记
- 标签：Astro、GitHub Pages、CI

专题不是分类的替代品。专题更像一个小册子或学习路径，用来把多篇文章串成体系。

## 11. 内容模型

使用 Astro content collections 管理内容。

文章 frontmatter：

```yaml
title:
description:
pubDate:
tags:
draft:
topic:
order:
background:
```

专题 frontmatter：

```yaml
title:
description:
status:
order:
background:
```

`background` 为文章和专题的必填字段，值来自 `src/data/backgrounds.ts` 中的背景 key。每个 key 同时声明桌面、移动资源及各自定位；内容集合 schema 和视觉校验脚本共同保证引用有效、资源存在且尺寸合格。新增文章或专题时，先制作独立背景并登记 key，再创建内容和提交 PR。

工具 frontmatter：

```yaml
title:
description:
slug:
category:
tags:
featured:
status:
```

项目 frontmatter：

```yaml
title:
description:
slug:
repo:
demo:
status:
tags:
cover:
```

生产构建必须排除 `draft: true` 的内容。

## 14. 实用工具页面

实用工具是一级导航，不隐藏在“更多”里。

设计参考 tool.lu 的工具箱思路，但视觉上要和博客统一，不做成外部工具站。

工具首页需要包含：

- 搜索框。
- 分类筛选。
- 精选工具。
- 工具卡片。
- 工具标题。
- 工具描述。
- 分类和标签。

本阶段已实现的第一批工具均为纯前端实现，不依赖后端：

- `/tools/json/`：JSON 格式化、压缩、校验。
- `/tools/base64/`：Base64 编码解码。
- `/tools/url/`：URL 组件编码解码。
- `/tools/timestamp/`：时间戳转换。
- `/tools/uuid/`：UUID v4 生成。
- `/tools/text-counter/`：字数统计。

`/tools/` 提供搜索和分类组合筛选。文本 diff、Markdown 预览、Mermaid 预览、正则测试等不属于首批已完成范围，是否实现留待后续需求单独确认。

实现要求：

- 每个工具有独立页面。
- 工具逻辑和 UI 分离。
- 工具输入、输出和复制操作只在当前浏览器中处理；不发送网络请求、不上传内容、不写入持久化存储，也不记录输入内容。
- 不为了工具页引入过重依赖。
- 工具页面在移动端也能使用。

新增工具的维护步骤：

1. 在 `src/data/tools.ts` 登记唯一 slug、路径、分类、搜索词和背景 key。
2. 在 `src/lib/tools/` 编写无 DOM 依赖的纯函数，并在 `tests/tools/` 覆盖成功、错误和边界输入。
3. 在 `src/pages/tools/` 创建使用 `ToolLayout` 的页面，采用关联标签、键盘焦点和 `aria-live` 状态；用户输入只能通过表单值或文本节点呈现，不能拼接为 `innerHTML`。
4. 为该工具制作独立桌面、移动 WebP 背景，在 `src/data/backgrounds.ts` 注册，并更新工具页面静态契约校验。
5. 运行 `npm run verify:tools`、`npm run verify:visual-background`、`npm run astro -- check` 和 `npm run build`，再执行桌面与移动端浏览器验收。

后续可扩展：

- 图片压缩。
- PDF 工具。
- Cron 表达式辅助。
- 颜色工具。
- 进制转换。
- 更多开发者工具。

依赖后端、AI 或复杂文件处理的工具放到后续阶段。

## 19. 访问统计与当前在线人数

访问统计和当前在线人数写入整体方案，但不进入第一批实现。

后续目标指标：

- 全站 PV。
- 全站 UV。
- 当前在线人数。
- 单篇文章阅读量。
- 单个工具访问量。

推荐后续架构：

- Cloudflare Worker 或类似 serverless 服务。
- D1 或 KV 存储。
- 浏览器本地生成匿名 visitorId。
- 页面加载调用 `/api/visit`。
- 页面活动期间每 30 秒调用 `/api/heartbeat`。
- 当前在线人数按最近 90 秒内有心跳的 visitorId 计算。

隐私原则：

- 不采集真实身份。
- 不存明文 IP。
- 不要求用户登录。
- 不在功能未实现时展示假统计。

设计预留：

- 页脚预留统计区域。
- 首页后续可展示总访问量和当前在线人数。
- 文章页后续可展示阅读量。
