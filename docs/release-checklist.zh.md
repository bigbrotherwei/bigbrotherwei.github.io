# 博客发布巡检清单

每次合并文章或功能 PR 时按顺序检查。PR 构建通过不等于 Pages 已发布；评论、访问统计则依赖站外服务，不作为静态页面构建的阻断条件。

## 合并前

1. 在目标分支运行 `npm run build`。确认 Astro、内容校验、Pagefind 和最终产物校验全部通过。产物校验会核对背景预加载、文章链接、RSS、Sitemap 与搜索索引。
2. 本地预览改动涉及的页面；涉及背景时至少看桌面和手机两种宽度，确认画面正确、文字可读、没有页面级横向滚动。涉及动画或交互时检查键盘焦点和“减少动态效果”。
3. PR 的 GitHub Actions `build` 通过后再合并。PR 阶段不会运行 `deploy`，不要把它当成线上更新。

## 合并后

1. 在 GitHub 仓库 **Actions → Deploy to GitHub Pages** 找到合并后由 `master` 触发的运行，确认 `build` 和 `deploy` 均成功，且提交对应刚合并的 PR。若只看到 PR 的 `build`，线上尚未完成发布；同时确认仓库 Pages 的发布源为 **GitHub Actions**。
2. 打开线上首页和本次改动的详情页。抽查一篇文章、一个专题和一个工具页面，确认各自背景可见、导航可用、文章图表/代码不冲出页面。手机窄屏至少检查本次改动的页面。
3. 在 `/search/` 输入一篇已发布文章的标题关键词，打开结果；确认 `/rss.xml` 可打开且最近文章出现在订阅内容中。新文章若未出现在搜索/RSS，先核对 Actions 构建产物和文章是否标为草稿。
4. 在一篇文章检查评论区：配置完成时应自动加载，可隐藏再显示；未配置时“评论未开放”不妨碍阅读。排查方法见[评论配置说明](comments-setup.zh.md)。
5. 在首页检查总访问量/累计访客，在文章或工具详情检查页面访问量。Vercount 被拦截或不可用时可能显示“暂不可用”，不代表 Pages 发布失败；排查方法见[访问统计说明](analytics-setup.zh.md)。

## 出现问题时

| 现象 | 先检查 | 处理方向 |
| --- | --- | --- |
| PR 或 `master` 的 `build` 失败 | Actions 的失败步骤和本地 `npm run build` | 修复代码或内容后重新提交；不要靠反复等待部署解决。 |
| `build` 成功但线上还是旧页面 | 同一运行的 `deploy` 状态、提交 SHA、Pages 发布源和浏览器缓存 | 等 `deploy` 完成后强制刷新；确认查看的是线上域名而非旧本地预览。 |
| 页面正常，评论未开放或加载失败 | Giscus 仓库变量、Discussions 和脚本请求 | 按评论配置说明修复；修改 Repository Variables 后需重新运行 Pages 构建。 |
| 页面正常，统计暂不可用 | 浏览器拦截、`events.vercount.one` 请求和 Vercount 状态 | 先排查第三方服务，不需要重发文章；正文和工具应保持可用。 |

若确认是新代码导致的线上回归，通过修复 PR 或回退该 PR 再部署。不要在 Pages 设置中切回 Jekyll 发布源。
